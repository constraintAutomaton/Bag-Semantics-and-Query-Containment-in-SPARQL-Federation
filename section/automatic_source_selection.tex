The problem is further compounded by the fact that there are two formalisms of federated queries: the SPARQL 1.1 Federated Query specification~\cite{w3SPARQLFederated} and \ac{ASSF}~\cite{Cheng2021}.
For \ac{CQ}, those two formalisms do not exhibit the same semantics.

\Cref{fig:bag-federation-example} illustrates this.
A federation of three members, an identifier registry, a job registry, and a social network, redundantly stores part of its data: each person's age and current job are recorded by both the job registry and the social network.
The federated query retrieves each person's job, age, e-mail, and identifier.
It is a \ac{CQ} \emph{without projection}, so on a single endpoint it would return a set.
Yet, given the definition of the canonical \ac{ASSF}, \ac{ESA}~\cite{Cheng2021}, evaluating it over the federation duplicates solutions, the solution mapping for \texttt{ex:jan} is returned 4 times, so the query exhibits bag semantics, even though every federation member contains a set-semantic \ac{KG}.
A similar query expressed with \texttt{SERVICE} clauses returns the same answer as a set.
