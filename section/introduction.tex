\section{Introduction}

Avoiding redundant computation is a central concern of query optimization.
Query containment is a classical problem underpinning such optimizations, including caching, view selection, query rewriting, and equivalence checking~\cite{Afrati2019-ch1, DOAN201221, Chaudhuri1993}.
Under set semantics, containment has been thoroughly characterized for many query fragments~\cite{Chandra1977, aho1979equivalences, aho1979efficient, Chekuri2000}.
Bag and bag-set semantic containment have also been studied~\cite{Chaudhuri1993, Afrati2010, khamis2021bag}; however, containment is undecidable for several fragments and some problems remain open.


\acp{KG} have become a widely adopted paradigm for representing and integrating heterogeneous data, supporting applications in scientific data management, knowledge representation, and the Web of Data~\cite{hogan2021knowledge}.
They are typically encoded as \ac{RDF} data, the W3C standard for graph-structured data, and queried with SPARQL, its companion query language.
SPARQL enables federation through the \texttt{SERVICE} operator~\cite{w3SPARQLFederated}, which executes a sub-query at a SPARQL endpoint identified by a URL.
This enables virtual data integration across distributed \ac{KG} sources, allowing heterogeneous data to be queried jointly without centralization.
This is particularly valuable when sources are governed by different policies, are maintained by independent parties, or are too large to consolidate.
Whether federation members are SPARQL endpoints on an internal network or exposed openly over the Web, federated queries impose substantial computational load on both endpoints and clients.\footnote{The open-Web setting can be fragile. Public SPARQL endpoints frequently experience downtime or performance degradation under load~\cite{buil2013sparql}.}
This cost is especially acute in workflows such as data analyses, where queries are routinely re-executed or iteratively refined.
Query optimization that avoids such re-execution is therefore highly desirable, and query containment is a foundational mechanism for achieving it.

Existing research on SPARQL query containment has focused on set semantics~\cite{WudageChekol2013, letelier2013static, chekol2012sparql, chekol2012sparql2, Stadler2018, jenaQC, Spasic2023}.
Yet the SPARQL query language operates under bag-set semantics~\cite{Perez2006, Angles2016}: the underlying database follows set semantics~\cite{w3ConceptsAbstract}, while query operators produce bags\footnote{A bag, or multiset, is similar to a set but allows duplicate elements.}~\cite{w3SPARQLQuery}.
Set-semantic containment does not imply bag-set semantic containment, so existing containment results do not apply to real-world SPARQL query optimization.
For example,\footnote{Inspired by \citeauthor{Chaudhuri1993}~\cite{Chaudhuri1993}.} \Cref{fig:bag-set-example} presents a containing query (a query whose results always include those of a contained query, regardless of the database) and a contained query.
The containing query retrieves the birthday of all people in the dataset, whereas the contained query refines it to those who have a job.
Under set semantics, the two queries are contained.
Under bag-set semantics, however, projecting away variables can introduce duplicates, which occurs in the example whenever an individual holds multiple jobs.\footnote{An executable example is provided at \url{https://github.com/constraintAutomaton/demo-semantic-query-containment-SPARQL} using the Comunica~\cite{taelman_iswc_resources_comunica_2018} query engine and the SpeCS~\cite{Spasic2023} SPARQL query containment solver.}

To the best of our knowledge, bag-set semantic SPARQL query containment remains unexplored, and query containment for federated queries has not been studied either.\footnote{Note that QCan~\cite{salas2018canonicalisation} addresses bag-set semantics, but for query equivalence rather than containment, by transforming SPARQL queries into a canonical form and performing syntactic comparison.}

This paper bridges these gaps by giving procedures for \ac{CQ} and \ac{UCFQ} containment in federated SPARQL under the semantics SPARQL evaluates, excluding nested queries.
To achieve this, we first introduce \ac{UCFQ}, a class that unions each triple pattern across several federation members and joins the results.
This class extends \ac{CQ} but lies inside \ac{UCQ}.
It is significant because it captures an important class of federated \acp{CQ} arising from automatic source selection strategies for SPARQL, where the federation engine assigns each triple pattern to the members that may answer it~\cite{Cheng2021}.
To decide containment for this class, we define the \ac{BFR}, a transformation from \ac{UCFQ} to \ac{CQ} under bag semantics.
We also introduce a bag-semantic reading of FedQPL~\cite{Cheng2021}, the logical query language for federated queries, as its set semantics is not in line with SPARQL query execution.
For federated \acp{CQ}, we reduce containment to containment of \acp{CQ} over located databases, which extend a triple with the federation member holding it, so that the results of the literature apply unchanged.
The procedures decide containment on the fragments where those results are exact, and report no answer on the others, as the general problem is open.
Next, we present an implementation of these procedures and a benchmark of federated query pairs,
on which we compare it with SpeCS~\cite{Spasic2023}, a set-semantics SPARQL query containment solver.
As its latest published version was not in a working state at the time of this study, we repaired it and extended its interface to control its timeout and memory limits.\footnote{Available at \url{https://github.com/constraintAutomaton/SpeCS/tree/fix/z3-path-from-env} and submitted upstream at \url{https://github.com/mirkospasic/SpeCS/pull/4}.}
Finally, we conclude the paper and outline future work.
