\section{Semantics of Federated SPARQL Queries}\label{sec:semantic_federated_q}

Before investigating query containment, we must establish under which semantics the different queries we study are evaluated.
This choice determines whether and how duplicate results can arise, which directly impacts how query containment is resolved.

\subsection{Single Endpoint Execution}\label{sec:single_endpoint}
SPARQL queries on single sources are evaluated under bag-set semantics.
The underlying \ac{KG} operates under set semantics~\cite{w3ConceptsAbstract}, whereas SPARQL operators produce bags.
The choice between bag and set semantics has a significant impact on the complexity and decidability of query containment~\cite{Chaudhuri1993}.
For relational \acp{CQ}, \citeauthor{Chaudhuri1993}~\cite{Chaudhuri1993} and \citeauthor{Afrati2010}~\cite{Afrati2010} established that only projection can increase the multiplicity of a result, and the same holds for SPARQL \acp{CQ}, whose only body operator, \texttt{JOIN}, cannot raise it.
In the context of \ac{UCQ}, the multiplicity can additionally be increased by \texttt{UNION} and by the combination of \texttt{UNION} and \texttt{JOIN}, as defined in \Cref{def_union_multiplicity,def_join_multiplicity}.
\acp{UCQ} are not the subject of our study; however, in the next sections we introduce \ac{UCFQ}, a subclass of \ac{UCQ}, together with the semantics of federated queries.



\subsection{Federated Query Execution}
A \ac{KG} is stored under set semantics, and querying a single endpoint operates under bag-set semantics.
A federated query, however, combines solution mappings drawn from several \acp{KG} at once, so it is not obvious whether spanning multiple members can introduce duplicate results.
The following proposition shows that it cannot, even when several federation members hold the same information.

\begin{proposition}\label{prop_service_bag_set}
  In a \ac{CQ}, a \texttt{SERVICE} clause returns a set of solution mappings, and therefore does not change the bag-set semantics under which the query is evaluated.
\end{proposition}

\begin{proof}
  The SPARQL federated query specification~\cite{w3SPARQLFederated} defines the execution of federated queries with \texttt{SERVICE} clauses as a join between the bag of solution mappings from the preceding execution and the bag of solution mappings returned by the SPARQL service.
  As presented in \Cref{sec:single_endpoint}, a join alone cannot increase the multiplicity of a bag.
  The specification does not apply a projection to the pattern of a \texttt{SERVICE} clause, so each federation member returns a set of solution mappings.
  Thus the service can only return a set, and does not affect the semantics of the SPARQL processing, which remains bag-set.
\end{proof}

\begin{remark}
  This argument holds only for \acp{CQ} without nested queries.
  A \texttt{SERVICE} clause holding a subquery with a projection could return duplicates, but the implications of such queries are outside the scope of this study.
\end{remark}

\subsection{\acl{UCFQ}}\label{sec:ucfq}

We define a particular class of federated queries, useful for capturing duplicate information held by different federation members.
Each triple pattern of the query body is evaluated across several members and the partial results are joined.

\begin{definition}[\acl{UCFQ}]\label{def_ucfq}
A \ac{UCFQ} is a multiway join $\fmj(U_1, \dots, U_n)$, optionally followed by a projection, where each operand $U_i = \fmu(\freq_{I_1}^{\mathit{tp}_i}, \dots, \freq_{I_{k_i}}^{\mathit{tp}_i})$ is a multiway union evaluating the same triple pattern $\mathit{tp}_i$ at a subset of federation members $I_1, \dots, I_{k_i}$.
We call each operand $U_i$ a \emph{branch} of the \ac{UCFQ}, and $\{I_1, \dots, I_{k_i}\}$ its \emph{sub-federation}.
The requests of $U_i$ may name the variables local to $U_i$ differently.
\end{definition}

A variable is \emph{local} to $U_i$ when the head does not select it and no other operand of the join binds it.
As nothing outside its request refers to such a variable, the request may name it freely without changing the result bag.

A \ac{CQ} is the special case where every union ranges over a single member, and every \ac{UCFQ} is a \ac{UCQ}, so the \acp{UCFQ} lie strictly between the \acp{CQ} and the \acp{UCQ}.
In particular, each triple pattern of a \ac{CQ} is the single-member union $\fmu(\freq_{\mathit{fm}}^{\mathit{tp}})$ over the member $\mathit{fm}$ at which it is evaluated.

\acp{UCFQ} can arise when a federation engine selects sources automatically, as it evaluates each triple pattern at every member that may answer it (\Cref{sec:related_works_fed}).
For instance, in a federation of a job registry and a social network, both members may store the job and birth date of a person.
The projection-free \ac{CQ} retrieving each person's job and birth date (\Cref{fig:ucfq-example}, top) would return a set on a single endpoint, but under \ac{ESA} it is evaluated as the \ac{UCFQ} (\Cref{fig:ucfq-example}, bottom), unioning each triple pattern across both members before joining the results.
Since both members hold the same solution for a person, the join returns that person with multiplicity four, even though every member stores a set. This duplication does not arise with explicit \texttt{SERVICE} clauses in a \ac{CQ}.%

\ac{ESA} is the particular case of \ac{UCFQ} in which every branch ranges over the entire federation $\{\mathit{fm}_1, \dots, \mathit{fm}_m\}$, formalized in \Cref{eq_esa}.
\begin{equation}
  \fmj\bigl(\fmu(\freq_{\mathit{fm}_1}^{\mathit{tp}_1}, \dots, \freq_{\mathit{fm}_m}^{\mathit{tp}_1}), \dots, \fmu(\freq_{\mathit{fm}_1}^{\mathit{tp}_n}, \dots, \freq_{\mathit{fm}_m}^{\mathit{tp}_n})\bigr)
  \label{eq_esa}
\end{equation}

\ac{ESA} can be classified as a join-over-union query plan.
Most federated engines produce join-over-union plans, for instance FedX~\cite{schwarte2011fedx}, SemaGrow~\cite{charalambidis2015semagrow}, and CostFed~\cite{saleem2018costfed}, which can likewise be rewritten as \acp{UCFQ}.
Automatic source selection can, however, produce \ac{CQ} plans of arbitrary shape, for instance, union-over-join plans~\cite{aimonier2024fedup}.
\ac{UCFQ} therefore does not capture every \ac{CQ} under automatic source selection.

Containment of \acp{UCQ} is undecidable under bag-set semantics (\Cref{sec:related_works_qc}), but the \acp{UCFQ} form a strict subclass, whose status this leaves open.
The next section introduces the \ac{BFR}, a transformation showing that evaluating a \ac{UCFQ} is equivalent to evaluating, under bag semantics, a \ac{CQ} whose triple patterns each read the \ac{BKG} of their branch's sub-federation.



\subsection{\acl{BFR}}\label{sec_bag_federation_reduction}

We propose the \ac{BFR}, a transformation that rewrites a \ac{UCFQ} as a \ac{CQ} evaluated over one \ac{BKG} per branch.
Intuitively, each branch's sub-federation becomes a virtual member holding the \ac{BKG} of its members, at which the branch's triple pattern is evaluated.

\subsection{A Bag-Semantic Reading of FedQPL}\label{sec_fedqpl}

We expressed the queries of the previous sections in the notation of FedQPL (\Cref{def_fedqpl}), an algebra that \citeauthor{Cheng2021}~\cite{Cheng2021} define under set semantics.
Its operators take and return sets of solution mappings, with $\fmu$ as set union~\cite[Def.~6]{Cheng2021}.
SPARQL, however, evaluates under bag-set semantics, as the underlying \acp{KG} are sets while the operators applied to them return bags.
We therefore read $\fmu$ and $\fmj$ as their bag counterparts, which aligns them with the SPARQL operators they lift.
\citeauthor{Cheng2021} do not adopt this reading and mention a bag semantics of FedQPL only as a direction for future research~\cite{Cheng2021}, which, to our knowledge, has not been pursued since.
This gap has practical consequences, as it leaves the answers of federated queries under automatic source selection ambiguous, so that engines may return different answers to the same query~\cite{tam2026strengthening}.
We justify our choice in the remainder of this section.

We first recall how FedQPL defines the result of a query over a federation, and against it the correctness of a source assignment.

\begin{definition}[Federation semantics and correctness, after \citeauthor{Cheng2021}~\cite{Cheng2021}]\label{def_fedqpl_correctness}
  The evaluation of a \ac{GP} $P$ over a federation $F$ is $[\![P]\!]_F = [\![P]\!]_{G_{\mathit{union}}}$, where $G_{\mathit{union}} = \bigcup_{f \in F} G_f$ is the set union of the \acp{KG} of the federation members~\cite[Def.~3]{Cheng2021}.
  A FedQPL expression $\varphi$ is \emph{correct} for a \ac{BGP} $B$ over $F$ if its result equals $[\![B]\!]_{G_{\mathit{union}}} = [\![B]\!]_F$~\cite[Def.~7]{Cheng2021}.
\end{definition}

This follows the stated intention that ``the result of a SPARQL query over such a federation should be the same as if the query was executed over the union of all the RDF data available in all the federation members'', and under set semantics \ac{ESA} is correct~\cite[Prop.~1]{Cheng2021}.
Under a bag-set reading it is not.

\begin{proposition}\label{prop_fedqpl_esa_incorrect}
Under bag-set semantics and ignoring projection, \ac{ESA} is not correct in general in the sense of \Cref{def_fedqpl_correctness}.
\end{proposition}

\begin{proof}
  Without projection, the evaluation of a \ac{BGP} over the set $G_{\mathit{union}}$ returns each solution mapping once (\Cref{sec:single_endpoint}).
  The \ac{ESA} expression of \Cref{eq_esa}, on the other hand, returns $\mu$ with multiplicity $\prod_{i} |\{\mathit{fm} \in F : \mu(\mathit{tp}_i) \in G_{\mathit{fm}}\}|$ by \Cref{def_union_multiplicity,def_join_multiplicity}.
  That multiplicity exceeds one as soon as two members hold a triple matched by the same $\mathit{tp}_i$ under $\mu$, in which case the two bags differ.
\end{proof}

Two readings would make \ac{ESA} correct again while keeping the federation semantics of \Cref{def_fedqpl_correctness} as stated.
The first assumes that no triple is duplicated across the federation members, so that the set union of their \acp{KG} coincides with their bag union, an assumption that is hard to verify in the open-Web setting and cannot always be enforced.
The second replaces the union of the plan by an operator that removes the duplicates across members while preserving those each member returns, which in general is more complex than a set union, and for \acp{UCFQ}, whose requests each return a set, reduces to a set union per branch.
Both depart from the bag union of SPARQL~\cite{w3SPARQLQuery}, and we adopt neither reading.

We propose instead to replace the set union $G_{\mathit{union}}$ by the \ac{BKG} of the federation (\Cref{def_bkg}).
The federation is then a bag rather than a set, so the reading moves from bag-set to bag semantics, which is the transition the \ac{BFR} performs (\Cref{sec_bag_federation_reduction}).
Applied to \Cref{eq_esa}, \Cref{prop_duplicate_fed_mem} states that the \ac{ESA} expression yields the same bag as evaluating the query body over the \ac{BKG} of the federation, which restores the correctness of \ac{ESA}.
This reading keeps the \texttt{UNION} of SPARQL and adds no operator to the algebra.
We adopt it for the remainder of the paper.
