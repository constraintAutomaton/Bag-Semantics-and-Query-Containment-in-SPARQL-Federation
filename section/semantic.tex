\section{Semantics of Federated SPARQL Queries}\label{sec:semantic_federated_q}

Before investigating query containment, we must establish under which semantics the different queries we study are evaluated.
This choice determines whether and how duplicate results can arise, which directly impacts how query containment is resolved.

\subsection{Single Endpoint Execution}
SPARQL queries on single sources are evaluated under bag-set semantics.
The underlying \ac{KG} operates under set semantics~\cite{w3ConceptsAbstract}, whereas SPARQL operators produce bags.
The choice between bag and set semantics has a significant impact on the complexity and decidability of query containment~\cite{Chaudhuri1993}.
In the relational-database setting, \citeauthor{Chaudhuri1993}~\cite{Chaudhuri1993, Afrati2010} established that for \acp{CQ} only projection can increase the multiplicity of a result.
The same property holds for SPARQL \acp{CQ}: the only body operator is \texttt{JOIN}, and \Cref{prop_cq_join_no_dup} shows that \texttt{JOIN} cannot raise the multiplicity, so projection at the head remains the only operator that can do so.
In the context of \ac{UCQ}, the multiplicity can additionally be increased by \texttt{UNION} and by the combination of \texttt{UNION} and \texttt{JOIN}, as defined in \Cref{def_union_multiplicity,def_join_multiplicity}.
\ac{UCQ} is not the subject of our study; however, in the next sections we introduce \ac{UCFQ}, a subclass of \ac{UCQ}, together with the semantics of federated queries.

\subsection{Federated Queries}
A \ac{KG} is set-semantic, and querying a single endpoint yields bag-set semantics.
A federated query, however, combines solution mappings drawn from several \acp{KG} at once, so it is not obvious whether spanning multiple members can introduce duplicate results.
We therefore examine the semantics of federated query evaluation.
The SPARQL federated query extension~\cite{w3SPARQLFederated} defines the execution of federated queries with \texttt{SERVICE} clauses as a join between the bag of solution mappings from the preceding execution and the bag of solution mappings returned by the SPARQL service.
\Cref{List:pseudoCodeFederatedQuery} presents the pseudo-code of this operation as taken from the specification~\cite{w3SPARQLFederated}.
By the SPARQL specification~\cite{w3SPARQLFederated}, the \ac{GP} inside a \texttt{SERVICE} clause has no projection, so each federation member returns a set of solution mappings.
A \texttt{SERVICE} clause is nested in the query through a \texttt{JOIN}, and \Cref{prop_cq_join_no_dup} shows that such a \texttt{JOIN} cannot increase the multiplicity.
Hence, even when some federation members hold duplicate information, the federated query produces no duplicate results, and \ac{CQ} evaluation with \texttt{SERVICE} clauses remains under bag-set semantics.

\subsection{\acl{UCFQ}}

We define a particular class of federated queries, useful for instance when one needs to capture duplicate information held by different federation members.
Each triple pattern of the query body is evaluated across several members and the partial results are joined, yielding a fragment strictly between the \acp{CQ} and the \acp{UCQ}.

\begin{definition}[\acl{UCFQ}]\label{def_ucfq}
A \ac{UCFQ} is a multiway join $\fmj(U_1, \dots, U_n)$ where each operand $U_i = \fmu(\freq_{I_1}^{\mathit{tp}_i}, \dots, \freq_{I_{k_i}}^{\mathit{tp}_i})$ is a multiway union evaluating the same triple pattern $\mathit{tp}_i$ at a subset of federation members $I_1, \dots, I_{k_i}$.
\end{definition}

A \ac{CQ} is the special case where every union ranges over a single member, and every \ac{UCFQ} is a \ac{UCQ}, so the \acp{UCFQ} lie strictly between the \acp{CQ} and the \acp{UCQ}.
Each triple pattern of the main query is a single-member union over the main endpoint $\mathit{fm}_g$, written $\fmu(\freq_{\mathit{fm}_g}^{\mathit{tp}})$.
\Cref{lst:ucfq_example} gives an example \ac{UCFQ} expressed in SPARQL 1.1 syntax~\cite{w3SPARQLFederated}, retrieving each person's age from the main endpoint and their job from two members.

Because the \acp{UCFQ} sit inside the \acp{UCQ}, their containment inherits the undecidability of bag-set \ac{UCQ} containment~(\Cref{sec:related_works_qc}).
To address this, the next section introduces the \ac{BFR}, a transformation showing that evaluating a \ac{UCFQ} is equivalent to evaluating a \ac{CQ} over one \ac{BKG} per union branch under bag semantics.



\subsection{\acl{BFR}}\label{sec_bag_federation_reduction}

We propose the \ac{BFR}, a transformation that rewrites a \ac{UCFQ} as a \ac{CQ} evaluated over one \ac{BKG} per union branch (\Cref{def_bkg}).
Intuitively, a virtual operator aggregates the members of each branch's sub-federation into a \ac{BKG} and evaluates the branch's triple pattern over it.

\subsection{Federated Queries Using Automatic Source Selection}\label{sec_fed_query_without_service}
Under automatic source selection, a query written as a \ac{CQ} can be evaluated as a \ac{UCQ}, and therefore return a bag rather than a set.
This happens when duplicate data is stored across several SPARQL endpoints of the federation, which the engine retrieves from each endpoint and combines by \texttt{UNION}.
The assignment of triple patterns to federation members is delegated to the query engine rather than expressed in the query syntax.
This mechanism is not defined in the SPARQL specification but has been formalized by \citeauthor{Cheng2021}~\cite{Cheng2021}.

A pattern matched by several members is returned once per member, and when the query joins several such patterns these multiplicities increase.
A projection-free \ac{CQ} can therefore return duplicate solution mappings, even though every member stores a set.

The canonical strategy of automatic source selection is \ac{ESA}, which sends every triple pattern to every federation member~\cite{Cheng2021}.
More performant strategies minimize the routing of triple patterns to federation members that cannot answer them, and optimize the size of the \ac{BGP} sent to each member, without sacrificing the completeness of the results.\footnote{A query engine may choose the \ac{ESA} strategy for its simplicity or to avoid analyzing which members to contact.}

\Cref{fig:bag-federation-example} makes this concrete.
A federation of three members, an identifier registry, a job registry, and a social network, redundantly stores part of its data, each person's age and current job are recorded by both the job registry and the social network.
The federated query retrieves each person's job, age, e-mail, and identifier.
It is a \ac{CQ} \emph{without projection}, so on a single endpoint it would return a set.
Yet under \ac{ESA} the query is in fact a \ac{UCQ} and returns a bag.
The age and the job of \texttt{ex:jan} are each answered by two members, so the join multiplies their two unions and the solution mapping for \texttt{ex:jan} is returned four times, even though every member contains a set-semantic \ac{KG}.
The \texttt{SERVICE} query of \Cref{fig:bag-federation-example} is the rewriting one would naturally write, yet it joins the members and returns the solutions as a set, so it does not reproduce this bag.\footnote{An executable demonstration of the semantics of federated queries, evaluated with the Comunica~\cite{taelman_iswc_resources_comunica_2018} query engine, is available at \url{https://github.com/constraintAutomaton/demo-federated-query-semantic}}

Such join-over-union plans can be rewritten into a \ac{UCFQ}, and the \ac{BFR} (\Cref{sec_bag_federation_reduction}) can transform this type of query as well.
Under \ac{ESA} every branch ranges over the whole federation, so the query reduces to a \ac{CQ} over a single \ac{BKG}, whereas a plan routing patterns to a subset of members reduces over one \ac{BKG} per branch.
