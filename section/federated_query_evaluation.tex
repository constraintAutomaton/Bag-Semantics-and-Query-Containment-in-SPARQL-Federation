\section{Federated Query Evaluation}\label{sec:federated_queries_query_containment}

In the context of query containment, federated queries initially appear fundamentally different from single-source query containment, as query containment is supposed to be data source independent whereas federated queries specify particular databases.
However, this difference is not fundamental.
We propose that for federated query containment, the IRIs of federation members must be considered, but not their content.
The fact that IRIs are referenced opens the door to optimizations by establishing guarantees about the lack of overlap between sources\rt{But there could be overlap, right? Same triple could exist at different endpoints.}, which could change the semantics of such queries without \texttt{SERVICE} clauses from bag to bag-set semantics.
However, this is not considered in this paper.
The following section explains our approach for federated queries.

\subsection{\ac{UDF} Particularities}
We define a \texttt{SERVICE} clause as a function $\mathit{Service}(\mathit{IRI}, P)$, where $\mathit{IRI}$ is the IRI of the target federation member and $P$ is the \ac{GGP} \rt{Unclear for the reader what GGP is}~\cite{w3SPARQLQueryFormal} associated with the service.
$P$ is transformed into a \texttt{SELECT} query where all the variables are projected as defined in the specification.\footnote{\url{https://www.w3.org/TR/2013/REC-sparql11-federated-query-20130321/\#algebra_service}}
In this paper, we do not consider nested \texttt{SERVICE} clauses.
Delegating the remote execution of a \texttt{SERVICE} clause to a third-party engine can raise load-management concerns and leaves the query issuer unable to guarantee that the endpoint supports federated query execution.
Furthermore, as shown in the proposition below, nested \texttt{SERVICE} clauses are semantically equivalent to a flattened form in which all \texttt{SERVICE} clauses appear at the basic graph pattern level.

\subsection{\ac{ASSF} Particularities}

Unlike \ac{UDF}, where \texttt{SERVICE} clauses make source assignment explicit in the query syntax, \ac{ASSF} delegates assignment to the query engine's source-selection algorithm.
\ac{ESA} is a specific instance of \ac{ASSF} where every triple pattern is sent to every federation member, so the source assignment is known prior to any computation.
Other \ac{ASSF} algorithms may assign triple patterns to a subset of members based on analytic queries~\cite{schwarte2011fedx} or metadata about the federation~\cite{gorlitz2011splendid}.\footnote{Some systems may determine their \ac{ASSF} algorithm during query planning.}

After source selection, the FedQPL plan trivially translates to a SERVICE-clause SPARQL query (we omit the construction), so the containment condition for \ac{UDF} applies uniformly to \ac{ASSF}.

Under \ac{DSA} \rt{To be honest, I'm getting lost in all these abbreviations...}, source assignments are not fixed at query-write time, so federated query containment cannot be resolved as a classical static analysis: at least partial query planning must be performed to determine the source assignment of each triple pattern.\rt{Clarify here that this may involve sending introspective queries to the endpoint, such as ASK queries}
The source assignment does not affect completeness of results, provided the \ac{ASSF} algorithm is sound, but it does affect the containment algorithm.
As established in \Cref{sec_fed_query_without_service} and \Cref{sec_bag_federation_reduction}, when the plan assigns triple patterns to multiple members, a \ac{CQ} becomes a \ac{UCQ}, which impacts the decidability and complexity of the containment check.
We propose using bag-semantic containment to avoid this decidability issue, at the cost of switching from bag-set to bag semantics for the containment criterion.
